# Exercise 3 — manifesting application quality

Iteration 3 of *Engineering AI-Driven Software Processes — Hands-on KGQA with LangGraph and LLMs*, Université Jean Monnet Saint-Étienne, WS 2026/2027.

**Today your bot gets a number.** Iteration 2 left you with two implementations of the same two contracts and no way to say which one ships. This session builds the thing that decides: test cases you write by hand, then test cases *generated* from a knowledge graph, an evaluator that runs both configurations over them and stores every run, and a report whose last line says pass or fail against a threshold you wrote down before you saw the result.

**What you build:** five hand-written cases per method, with the split between what is *exact* (a refusal) and what is a *rate* (a recognition); an extension of the domain knowledge graph — **ten cities and three pizzas picked from the API itself**, ten streets and their house numbers written by you — that makes the generator produce sentences it could not produce before; four evaluation runs — first varying the number of cases, then the model, on the same cases; and a generated `quality-report.md` with a delta and a gate.

**What you do not build:** the catalog, the generator and the evaluator. They are in this folder, they work, and they are commented for reading. The point of the session is what you *put into* them and what you read *out of* them — this is the iteration where the artifact you deliver is a number, not a feature.

## Glossary

Eight words this sheet uses constantly, on top of the Iteration 1 and 2 glossaries.

| word | what it means here |
| --- | --- |
| **catalog** | the knowledge graph in `benchmark/data/*.ttl`: the pizzas, addresses, streets and cities a generated sentence can talk about, each with its canonical value and every wording a user might write for it. |
| **pattern** | a sentence with slots, in `model.ttl`: `{ORDER} {ARTICLE?} {PIZZA} to {ADDRESS:STREET}, …`. A slot is a **class**; the individual drawn for it *is* the expected value. |
| **benchmark** | a named set of patterns: `address_v2` (one component), `pizza_v2` (one component), `order_v2` (two components in one sentence). The three floors of the test pyramid, in data. |
| **capacity** | how many *different* sentences the catalog can currently produce for a benchmark. Ask for more cases than that and the generator warns you — which is a statement about your data, not about the harness. |
| **refusal case** | a case whose expected value is `None`: a pizza we do not sell, a city we do not deliver to. Recognising nothing is the right answer, and a benchmark without such cases measures half a contract. |
| **seed** | the number that makes a random draw reproducible. It travels with every case and into every result file; a metric whose seed is unknown cannot be re-run. |
| **confidence interval** | what a rate over *n* cases actually claims. 20 of 20 is not 1.00 — it is [0.84, 1.00]. It is why generating cases is worth doing: the interval shrinks with *n*, and the threshold is compared against its **lower end**. |
| **gate** | two things in this repository, related on purpose: the `pytest -m gate` marker (did *you* do the task) and the last line of `quality-report.md` (does the *bot* ship). Both are decisions written down before the result was known. |

## Task 2 — your hand-written test cases [20 min]

**File for this task:** `tests/test_manual_cases.py` (a skeleton with one case per method; you add four more each).

Before anything is generated, you write cases yourself. Fifteen of them: five per method, at least one refusal per method. Writing them is how you find out what your bot actually promises — and the generated set later has to be compared against something a human chose.

### 2a — write the cases [12 min]

Open `tests/test_manual_cases.py` and fill `MANUAL_ADDRESS`, `MANUAL_PIZZA` and `MANUAL_ORDER`. A case is a pair: what the user types, and what the component must write into the slot. `None` means **the component must recognise nothing**.

Cover these five kinds, one case each — they are the ones that find something:

1. the canonical form, the one your bot obviously handles;
2. a different word order or sentence shape;
3. a spelling a real customer uses (`St. Etienne`, `Margaritha`, `12 b`);
4. a **half** input — street and city but no number, a sentence with no pizza — expected `None`;
5. something outside the domain — a city we do not deliver to, a pizza we do not sell — expected `None`.

Write the expected value from the **contract**, not from what your bot currently does. A case written to match the implementation can never fail, and a test that can never fail is documentation with a runtime cost.

### 2b — run them against both configurations [8 min]

```bash
pytest -q -m gate tests/test_manual_cases.py       # did you write five per method, with a refusal?
pytest -q tests/test_manual_cases.py -rs           # the static configuration
BOT_CONFIG=llm pytest -q tests/test_manual_cases.py -rs   # the LLM configuration
```

Three tests per method run over your cases, and the difference between them is the lesson:

* **refusals are exact.** `test_a_refusal_is_never_answered_with_a_value` allows no misses. "Nothing recognised → write nothing" is a guarantee, and a guarantee that holds four times out of five is not a guarantee.
* **recognitions are a rate.** `test_pass_rate_over_the_hand_written_cases` compares against `THRESHOLD` (0.80) and prints the interval. Over five cases that interval is embarrassingly wide — look at it, and remember it in Task 4.

**Check:** the gate run is green (3 passed), and you can name one case the static configuration fails and one the LLM configuration fails. They will not be the same case. If a test is red, decide honestly which side is wrong — your expected value or the component — and fix that one. Fixing a case because the bot disagrees with it is how a test suite stops meaning anything.

**Commit** at the end of this task.

## Task 3 — pick your instances, write your streets [25 min]

**Files for this task:** `benchmark/fetch.py` (given — the tool that talks to the API), `benchmark/data/picked.ttl` (created by it), `benchmark/data/catalog.ttl` and `benchmark/data/model.ttl` (yours to edit).

Five hand-written cases per method gave you an interval about half as wide as the number itself. You do not fix that by typing sixty more cases; you fix it by **adding to the catalog**, because every individual and every wording you add multiplies into sentences the generator can draw.

But not everything in the catalog is yours to invent. **The service owns what can be ordered and where we deliver** — a pizza id is the one `POST /order` wants, and a delivery city is one `GET /city` lists. Type those by hand and your benchmark measures a world that does not exist. **You own the streets, the house numbers and the wordings** — no endpoint has them, and they are what makes the benchmark yours.

| what | was | must be | where it comes from |
| --- | ---: | ---: | --- |
| cities | 8 | **18** | `python -m benchmark.fetch cities "…"` — ten more, from `GET /city` |
| pizzas | 10 | **13** | `python -m benchmark.fetch pizzas "…"` — three more, from `GET /pizza` |
| streets + house numbers + addresses | 8 | **18** | Turtle, by hand |
| descriptive pizza wordings | 8 | **11** | one `rdfs:label` each, by hand |

### 3a — pick ten cities and three pizzas from the endpoint [8 min]

Browse first, then pick. Pick cities you can say something about — the ones around Saint-Étienne, the ones your team comes from, one with an accent, one with a hyphen, one whose name a French keyboard makes hard:

```bash
python -m benchmark.fetch cities --search saint-eti          # look
python -m benchmark.fetch cities "Grenoble" "Roanne" "Firminy" "Montbrison"   # pick
python -m benchmark.fetch pizzas --list
python -m benchmark.fetch pizzas "Capricciosa" "Tartufo" "Rucola"
```

Everything lands in `benchmark/data/picked.ttl` — a new file next to `catalog.ttl`, which `Catalog()` picks up because it reads *every* `.ttl` in that directory. Each individual carries the service's own spelling, its lower-case form and a line saying where it came from:

```turtle
:grenoble a :CITY ; :name "Grenoble" ; :deliverable true ;
    rdfs:label "Grenoble", "grenoble" ;
    tg:source "GET /city" ; tg:fetchedAt "2026-09-18"^^xsd:date .
```

Three things the tool will refuse to do, each for a reason worth a sentence in your team:

* a city the service has never heard of — it is not in the delivery area, so a case built from it measures the error message and not the bot;
* a pizza that is not on the menu — `GET /pizza` is the contract, and an id nobody serves is not a test case;
* a name that is **already in the graph** — this is the "a city is defined exactly once" rule, enforced where it would be broken. Your second address in Lyon writes `:hasCity :lyon`; it does not write Lyon again.

### 3b — write the ten streets, and the wordings [12 min]

The service validates a street; it does not list one. So this half is Turtle, in `catalog.ttl` (or in `picked.ttl` under your own heading — same directory, same graph):

```turtle
# an address in a city you PICKED -- link to it, never repeat it
:a13 a :ADDRESS ; :hasStreet :st13 ; :hasStreetNumber :sn13 ; :hasCity :grenoble .
:st13 a :STREET       ; :name "Cours Jean Jaurès" ;
    rdfs:label "Cours Jean Jaurès", "Cours Jean Jaures", "C. Jean Jaurès" .
:sn13 a :STREETNUMBER ; :name "77" ; rdfs:label "77", "no 77" .

# a descriptive wording on a pizza -- what it IS, not another spelling of its name
:Tartufo rdfs:label "truffle pizza", "the truffle one" .
```

Spread the ten addresses over cities that already existed **and** the ones you picked: at least three cities have to serve two addresses each, or `test_cities_are_reused_by_several_addresses` fails — for the right reason.

*If you have time:* add one **pattern** to `model.ttl` — another word order, the delivery-only phrasing. A pattern multiplies with everything in the catalog, so it is the cheapest way to raise capacity, and it is the part of the meta model the lecture is really about.

### 3c — check it [5 min]

```bash
pytest -q                                      # the data tests, and your picks against the live service
pytest -q -m gate tests/test_extension.py      # the task: enough, picked where they had to be picked
python -m benchmark.generate --capacity        # the numbers from Task 1b, now bigger
python -m benchmark.generate --benchmark address_v2 -n 5 --seed 99   # read five of your new sentences
```

**Check:** both `pytest` runs green, and the capacity numbers have grown. Write down capacity **before** and **after** — two of the four numbers of your deliverable. `pytest -q` also compares every `:deliverable` flag and every `:pizzaId` in your graph against the live API, so a city you typed instead of picking is named on the spot (that test skips when the API is unreachable — then start `pizza_api_stub.py`, which serves the same delivery area offline).

**Commit** the extension as its own commit: `picked.ttl` and your streets together. It has to be reviewable as a diff — that is how a team of four extends one benchmark without a merge conflict.

## Task 4 — the evaluation runs: more cases, then another model [20 min]

**File for this task:** `evaluate.py` (given — read the module docstring and `score()`; they are the whole harness).

The evaluator takes the two things that decide what a number means: **how many cases** and **which model**. They answer two different questions, and this task asks both:

* `-n` changes **how sure** you are about one implementation — the accuracy barely moves, the interval shrinks.
* `--model` changes **which implementation** you are measuring at all. A different model is not a setting; it is a different program behind the same contract, and it has to be re-measured from scratch.

Every run draws `n` cases **per method** from your extended graph, scores them, writes `results/last-run.json`, appends a line to `results/history.jsonl`, regenerates `quality-report.md`, and **compares itself with the run before it**.

### 4a — three runs, one model: what more cases buy [8 min]

```bash
python evaluate.py --model mistral-small-4-119b -n 5  --seed 42
python evaluate.py --model mistral-small-4-119b -n 15 --seed 42
python evaluate.py --model mistral-small-4-119b -n 30 --seed 42
```

**Watch the interval, not the accuracy.** Three of five is 0.60 with an interval something like [0.23, 0.88] — a number that permits almost any opinion. The same rate over thirty cases still says 0.60, and says it between 0.42 and 0.75. You did not make the bot better; you made the statement about it stronger, and that is the entire argument for generating test cases.

**Check:** three lines in `results/history.jsonl`, and you can say which of the three numbers you would be willing to put in front of the room.

### 4b — the same cases, two models: what the model buys [10 min]

Now hold everything else still. **Same `-n`, same `--seed`, same knowledge graph** — so the generator draws exactly the same sentences — and change only the model:

```bash
python evaluate.py --model mistral-small-4-119b   -n 15 --seed 42     # you already have this one
python evaluate.py --model qwen-3.6-35b-instruct  -n 15 --seed 42
```

`.env.example` lists the models the room has been given: `mistral-small-4-119b` (the default), `qwen-3.6-35b-instruct` (clean JSON, fastest), `gemma-4-31b`, `llama-3.1-8b`. Take a third if you have time — the runs are cheap and the table is more interesting with three rows.

This is the one comparison in the session where the delta block says something exact. With `-n` and `--seed` unchanged the two runs saw **the same sentences**, so the harness can tell you not only that the rate moved but *which cases changed their mind*:

```text
    method                  before   after    delta       interval now
    address_recognition       0.53    0.73    +0.20   [0.48, 0.89]

    45 sentence(s) occur in both runs: 4 now pass, 1 now fail.
      regression: Bring it to n° 34 Rue Ferdinand in Saint-Priest-en-Jarez
```

The harness also prints a warning on such a run — *"different configuration or model: this is a comparison of two implementations, not of two runs of the same one"* — and it is there on purpose. A model swap re-opens every question the first measurement closed: latency (`p50 s` in the table), the failure modes, and whether the fenced-JSON handling of Iteration 2 still holds.

Three things to write down while the two runs go past:

1. **The regression.** Almost every model swap that raises the average also breaks something that used to work. Find one such case and read it — that single sentence is worth more in the closing round than the average.
2. **Latency.** Compare `p50 s`. A model that is three points better and twice as slow is a trade, not an improvement, and it is your team's call which one you would ship.
3. **Nondeterminism.** Run *one* configuration twice with the same `-n`, the same seed and the same model. At least one number moves. That is the nondeterminism of Lecture 3 in your own terminal — and the reason a delta smaller than that wobble is not a result.

### The other flags [2 min]

```bash
python evaluate.py --config static -n 30                       # the baseline: no model, no key, no network
python evaluate.py --data benchmark/data/catalog.ttl -n 10     # a specific knowledge graph file
python evaluate.py --method address_recognition -n 50          # one method only, when time is short
python evaluate.py --threshold 0.9 -n 30                       # the gate -- decide this BEFORE the run
```

**Check for the whole task:** `results/history.jsonl` has **at least four lines**, at least two `cases_per_method` values and at least two different models in them, and for every pair of consecutive runs you can say *why* the numbers differ — more cases, another seed, another model, or the bot itself. If you cannot tell which, that is the finding; say it in the closing round.

> **Budget.** One case is one model call, and `pizza_and_address` makes two, so `-n 15` is about 60 calls per run. `check_setup.py` printed the latency of a single call — multiply. If you are short on time, run 4b at `-n 10` rather than dropping it: the model comparison is the part of this task the report is built on.

## Task 5 — the report and the decision [10 min]

`quality-report.md` was written by the last run. Open it. It has what makes a number honest — commit, model, `n`, seed, date, wall clock — a row per method with the delta against the previous run, the table of every run so far, and a gate line.

Do three things:

1. **Read the gate line out loud** in your team. It compares the *lower end* of the interval of the weakest method with your threshold. If it says FAIL, there are exactly two honest responses: make the component better, or measure more cases and see whether the interval alone was the problem. Lowering the threshold after seeing the number is not one of them.
2. **Decide which configuration and which model ship**, and name the number that decided each. The "Runs so far" table at the bottom of the report is your model comparison: one row per run, with the model in it. A measured "we do not ship the LLM configuration" is the strongest possible outcome of this session — and one of the more common ones; so is "the cheaper model is within the interval of the bigger one, so we ship the cheaper one".
3. **Add three lines by hand** at the bottom of the report, under a heading of your own (the generator will not touch them if you put them in a separate file — otherwise keep them in your commit message): the capacity before and after Task 3, the interval before and after, and one **generated sentence your bot gets wrong**, with the error category you would put it in.

**Commit** `quality-report.md`, `results/` and your extended `catalog.ttl` together.

## Troubleshooting

| what you see | what it means | what to do |
| --- | --- | --- |
| `address_recognition` accuracy near 0.00 | the Pizza API is unreachable, so every address fails validation | `python pizza_api_stub.py` in a second terminal, `PIZZA_API_BASE=http://127.0.0.1:8000` in `.env` |
| `UserWarning: … cases requested, but the catalog can only produce …` | your `-n` is larger than the capacity of that benchmark | Task 3: add wordings and individuals — or lower `-n` |
| `pytest -q` red after editing the Turtle file | a data rule broke | read the assertion: it names the individual and the rule (duplicate wording, missing `:name`, city defined twice, street with no address) |
| `pytest -q -m gate` red | you have not finished Task 2 or Task 3 | the message says which count is missing and how many |
| every LLM run takes minutes | `-n` times three methods times one call each (the third method makes two) | start with `-n 5`, and use `--method` while you are still reading output |
| the LLM configuration scores exactly like the static one | the service is failing and the fallback is answering every time | `python check_llm.py`; a tier line saying `static` on every case means no model answer arrived |
| `GET /city -> HTTP 404` | the API you are pointing at is older than service version 1.2.0 | use the live service, or `python pizza_api_stub.py`, which serves the same area offline |
| `benchmark.fetch` refuses a city you are sure exists | the service spells it differently (`Saint-Étienne`, not `St-Etienne`) | `python -m benchmark.fetch cities --search <first letters>` and copy the spelling it prints |
| `results/last-run.json` not found after a run | you ran the script from another directory | run it from the folder that contains `evaluate.py` |
| the numbers move although nothing changed | the LLM configuration is nondeterministic | that is the finding of item 6 of the lecture's definition of done — record it, do not hide it |
