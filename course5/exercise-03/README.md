# Exercise 3 — manifesting application quality

Iteration 3 of *Engineering AI-Driven Software Processes — Hands-on KGQA with LangGraph and LLMs*, National and Kapodistrian University of Athens, WS 2026/2027.

**Today your bot gets a number — and the number decides.** Iteration 2 left you with two implementations of the same two contracts, static and LLM, and no way to say which one ships. This session builds the thing that decides: test cases you write by hand, test cases *generated* from a knowledge graph, an evaluator that runs **both configurations over the same cases** and stores every run, and a report that applies a **quality gate** you wrote down before you saw the result.

**What you build:** five hand-written cases per method, with the split between what is *exact* (a refusal) and what is a *rate* (a recognition); an extension of the domain knowledge graph — **ten cities and three pizzas picked from the API itself**, ten streets and their house numbers written by you — that brings new places and new failure modes into the benchmark; a threshold, written down and committed **before** the first decisive run; four runs of one run plan — the static baseline, the LLM candidate on the same cases, the same run again, another model; and a generated `quality-report.md` with the quality gate and the paired comparison.

**What you do not build:** the catalog, the generator and the evaluator. They are in this folder, they work, and they are commented for reading. The point of the session is what you *put into* them and what you read *out of* them — this is the iteration where the artifact you deliver is a number, not a feature.

## Glossary

The words this sheet and Lecture 3 use, one meaning each, on top of the Iteration 1 and 2 glossaries.

| word | what it means here |
| --- | --- |
| **catalog** | the knowledge graph in `benchmark/data/*.ttl`: the pizzas, addresses, streets and cities a generated sentence can talk about. |
| **individual** | one thing in the catalog: `:athens`, `:a1` (an address), `:Margherita`. Its canonical value is `:name`; drawn for a sentence, it *is* the expected value. |
| **wording** | one way to write an individual, an `rdfs:label`: `"Athens"`, `"ATHENS"`, `"Athina"`, `"Αθήνα"` for `:athens`. Every wording of a deliverable city must be one the service accepts — `pytest -q` checks that. |
| **pattern** | a sentence with slots, in `model.ttl`: `{ORDER} {ARTICLE?} {PIZZA} to {ADDRESS:STREET}, …`. A slot is a **class**; one individual is drawn for it, one of its wordings is rendered. |
| **benchmark** | a named set of patterns: `address_v2` and `pizza_v2` measure one component each — the bottom floor of the test pyramid — and `order_v2` two components in one sentence, the middle floor. The top floor, whole dialogs, is not generated in this session. |
| **method** | one benchmark and the component(s) it runs: `address_recognition`, `pizza_recognition`, `pizza_and_address`. The unit `evaluate.py` reports and the quality gate decides on. |
| **capacity** | how many *different* sentences the catalog can produce for a benchmark — a reachability check: what you add counts only if a pattern can draw it. |
| **refusal case** | a case whose expected value is `None`: a pizza we do not sell (`Pizza Napoli`), a city we do not deliver to (`Barcelona`). Recognising nothing is the right answer. Writing a value instead is a **refusal violation** — the worst error, a wrong order. |
| **comparison rule** | when an answer counts as right: it names the **same individual** as the expected value — any of its wordings, compared without case, accents and stray spaces — and a refusal is right when nothing is written. `score()` in `evaluate.py`, for generated and hand-written cases alike. |
| **accuracy** | hits / n under the comparison rule, per method. |
| **seed** | the number that makes a random draw reproducible. Same catalog, same `n`, same seed → the same cases under the same ids. |
| **confidence interval** | what a rate over *n* cases actually claims (Wilson, 95 %). 20 of 20 estimates 1.00; the data are compatible with anything from 0.84 up. All *n* of *n* reach a lower end of `t` only if `n ≥ 3.84·t/(1−t)`: **16 for 0.80, 35 for 0.90**. |
| **quality gate** | the rule that decides whether a configuration ships, written down before the run: (1) for every method the lower end of the 95 % interval ≥ your threshold, (2) no refusal violation, (3) p95 latency ≤ 3 s. PASS means the data show the accuracy is above the threshold (one-sided, about 97.5 %); FAIL means only that they do not show it — not that it is below. Not to be confused with the `pytest -m gate` **marker**, which asks whether *you* did the task. |
| **baseline** | the static configuration, measured on the same cases as the candidate (R1). |
| **candidate** | the configuration under test — the LLM configuration with a given model (R2, R4). |
| **delta** | the *paired* difference between two runs over the same cases: b cases now pass, c now fail, and the McNemar test of b against c. |
| **change** | the difference in accuracy to the previous run, whatever it was — paired or not. |
| **harness** | everything around the bot that measures it: generator, `evaluate.py`, the tests. |
| **gold standard** | the expected values, written from the contract — here, the drawn individuals and your hand-written expected values. |

## Task 2 — your hand-written test cases [20 min]

*Slides: 3.7 (statistical unit tests), 3.13 (the gold standard and the comparison rule), 3.29 (component tests).*

**File for this task:** `tests/test_manual_cases.py` (a skeleton with one case per method; you add four more each).

Before anything is generated, you write cases yourself. Fifteen of them: five per method, at least one refusal per method. Writing them is how you find out what your bot actually promises — and the generated set later has to be compared against something a human chose.

### 2a — write the cases [12 min]

Open `tests/test_manual_cases.py` and fill `MANUAL_ADDRESS`, `MANUAL_PIZZA` and `MANUAL_ORDER`. A case is a pair: what the user types, and what the component must write into the slot. `None` means **the component must recognise nothing**.

Cover these five kinds, one case each — they are the ones that find something:

1. the canonical form, the one your bot obviously handles;
2. a different word order or sentence shape;
3. a spelling a real customer uses (`Athina`, `Margaritha`, `12 b`);
4. a **half** input — street and city but no number, a sentence with no pizza — expected `None`;
5. something outside the domain — a city we do not deliver to, a pizza we do not sell — expected `None`.

For the order method, the refusal is a sentence in which **neither** is recognisable: `(None, None)`. A case with one of the two (`("a Funghi to Barcelona", (5, None))`) is worth writing too — it tests that one component does not drag its neighbour down.

Write the expected value from the **contract**, as the catalog names it (`"Athens"`, `"12b"`), not from what your bot currently does. The comparison rule takes care of spellings: `"Athina"` or `"12 b"` for the same individual count as right — here exactly as in `evaluate.py`.

### 2b — run them against both configurations [8 min]

```bash
pytest -q -m gate tests/test_manual_cases.py       # did you write five per method, with a refusal?
pytest -q tests/test_manual_cases.py               # the static configuration
BOT_CONFIG=llm pytest -q tests/test_manual_cases.py   # the LLM configuration
# PowerShell: $env:BOT_CONFIG="llm"; pytest -q tests/test_manual_cases.py
```

Two statements over the same cases, and the difference between them is the lesson:

* **refusals are exact.** `test_a_refusal_is_never_answered_with_a_value` allows no miss: "nothing recognised → write nothing" is a guarantee, and a guarantee that holds four times out of five is not a guarantee.
* **recognitions are a rate — and five cases cannot decide a rate.** Even 5 of 5 has a lower bound of 0.57. So the rate is *reported*, not asserted: the section *your hand-written cases* at the end of the pytest output lists every case, what the component wrote, and the interval.

**Check:** the gate run is green (3 passed), and the summary shows one case the static configuration misses and one the LLM configuration misses. They will usually not be the same case. If a refusal test is red, decide honestly which side is wrong — your expected value or the component — and fix that one. Fixing a case because the bot disagrees with it is how a test suite stops meaning anything.

**Commit** at the end of this task.

## Task 3 — pick your instances, write your streets [25 min]

*Slides: 3.13 (who owns which data), 3.23 (why a knowledge graph), 3.24 (one address, many wordings), 3.26 (three benchmarks, and what the interval is about).*

**Files for this task:** `benchmark/fetch.py` (given — the tool that talks to the Pizza API), `benchmark/data/picked.ttl` (created by it), a Turtle file of your own for the streets.

The handed-out catalog has eight addresses: two hundred generated address cases are two hundred sentences about **eight places**, and cases drawn from the same place fail together. More sentences do not fix that; **more individuals do** — new cities, two-word names, transliterations, streets with a date in their name. That is what this task adds: coverage, new failure modes, more distinct individuals behind every interval.

Not everything in the catalog is yours to invent. **The service owns what can be ordered and where we deliver** — a pizza id is the one `POST /order` wants, a delivery city is one `GET /city` lists. Type those by hand and your benchmark measures a world that does not exist. **You own the streets, the house numbers and the wordings** — no endpoint has them.

| what | was | must be | where it comes from |
| --- | ---: | ---: | --- |
| cities | 8 | **18** | `python -m benchmark.fetch cities "…"` — ten more, from `GET /city` |
| pizzas | 11 (ten on the menu, `Pizza Napoli` not) | **14** | `python -m benchmark.fetch pizzas "…"` — three more, from `GET /pizza` |
| streets + house numbers + addresses | 8 | **18** | Turtle, by hand |
| descriptive pizza wordings | 8 | **11** | one `rdfs:label` each, by hand |

**Work in parallel without conflicts:** one person runs `fetch` for the team (it appends to the single `picked.ttl`); everyone else writes their streets into a file of their own, `benchmark/data/streets-<name>.ttl` — `Catalog()` reads every `.ttl` in that directory into one graph.

### 3a — pick ten cities and three pizzas from the endpoint [8 min]

Browse first, then pick. Pick cities you can say something about — the ones around Athens, the ones your team comes from, one whose name is two words, one whose Latin spelling is not the one you would have typed:

```bash
python -m benchmark.fetch pizzas --list                   # the twenty-two pizzas GET /pizza lists
python -m benchmark.fetch cities --search patr            # the delivery area, searched
python -m benchmark.fetch cities "Patras" "Marousi" "Kifisia" "Glyfada"   # pick
python -m benchmark.fetch pizzas "Capricciosa" "Tartufo" "Rucola"
```

The delivery area is **every commune of France and every town and village of Greece**, plus Leipzig, Halle and Dresden — about 43 000 names — so `GET /city` answers a page, not a list. Everything you pick lands in `benchmark/data/picked.ttl`, with the service's own spelling, its lower-case form and a line saying where it came from:

```turtle
:patras a :CITY ; :name "Patras" ; :deliverable true ;
    rdfs:label "Patras", "patras" ;
    tg:source "GET /city" ; tg:fetchedAt "2026-09-30"^^xsd:date .
```

The tool refuses three things, each for a reason worth a sentence in your team: a city the service has never heard of (a case built from it measures the error message, not the bot); a pizza that is not on the menu (`GET /pizza` is the contract); a name that is **already in the graph** — "a city is defined exactly once", enforced where it would be broken. Your second address in Piraeus writes `:hasCity :piraeus`; it does not write Piraeus again.

### 3b — write the ten streets, and the wordings [12 min]

**Reading Turtle in four lines:** `:s :p :o .` is one statement — subject, property, value, full stop. `a` means "is a" (`rdf:type`). `;` continues with the **same subject**, `,` gives the **same property** another value. `:x` is an individual or a class (an IRI), `"…"` is text (a literal); `tg:` is the vocabulary of the test generator.

```turtle
# an address in a city you PICKED -- link to it, never repeat it
:a13 a :ADDRESS ; :hasStreet :st13 ; :hasStreetNumber :sn13 ; :hasCity :patras .
:st13 a :STREET       ; :name "Agiou Nikolaou" ;
    rdfs:label "Agiou Nikolaou", "Ag. Nikolaou", "Agiou Nikolaou Street" .
:sn13 a :STREETNUMBER ; :name "77" ; rdfs:label "77", "no 77" .

# another wording of a city you picked -- one the service accepts
:patras rdfs:label "Patra", "Πάτρα" .

# a descriptive wording on a pizza -- what it IS, not another spelling of its name
:Tartufo rdfs:label "truffle pizza", "pizza with truffles" .
```

Spread the ten addresses over cities that already existed **and** the ones you picked: at least three cities have to serve two addresses each, or `test_cities_are_reused_by_several_addresses` fails — for the right reason.

**A city wording must be one the delivery check accepts.** `pytest -q` sends every wording of every deliverable city to `POST /address/validate`. `--search` *finding* a spelling does not mean the delivery check accepts it: `--search halandri` lists Chalandri, but `"Halandri"` is refused. A refused wording is not a hard case — the contract says "write nothing" for it, so a case expecting the address would be a wrong gold standard.

*If you have time:* add one **pattern** to `model.ttl` — another word order, the delivery-only phrasing. A pattern multiplies with everything in the catalog.

### 3c — check it [5 min]

```bash
pytest -q                                      # the data tests, and your picks against the live service
pytest -q -m gate tests/test_extension.py      # the task: enough, picked where they had to be picked
python -m benchmark.generate --capacity        # reachable: the numbers from Task 1b, now bigger
python -m benchmark.generate --benchmark address_v2 -n 5 --seed 99   # read five of your new sentences
```

**Check:** both `pytest` runs green, and the capacity numbers have grown — what you added is reachable from a pattern. `pytest -q` also compares every `:deliverable` flag, every `:pizzaId` and every city wording against the live API (those checks skip when the service does not answer in time — run again, or start `pizza_api_stub.py`). A Turtle mistake is named with its file and line.

## Task 4 — the run plan R1–R4 [20 min]

*Slides: 3.15 (the quality gate and the decision rule), 3.17 (re-measuring), 3.21 (how many cases a decision needs), 3.34 (what the harness prints), 3.35 (the paired comparison).*

**File for this task:** `evaluate.py` (given — read the module docstring and `score()`; they are the whole harness).

Every run draws `n` cases **per method** from your extended graph, scores them, applies the quality gate, writes `results/last-run.json`, appends a line to `results/history.jsonl`, regenerates `quality-report.md` — and **pairs itself with the run before it** when both saw the same cases (same graph, `n` and seed): b cases now pass, c now fail, and the exact McNemar test says whether b and c differ by more than chance.

### 4.0 — write the threshold down [1 min]

Before the first decisive run, decide the threshold of clause (1) — per method, with one reason — and write it into `quality-notes.md` (the template is in Task 5). **Commit it.** The commit time is the proof that it came before the number. Then pass it on every run: `--threshold 0.80` (or yours).

### The run plan

Run them in this order, from the folder that contains `evaluate.py`. Each run is compared with the one before it.

| run | command | compared with | what it shows | about |
| --- | --- | --- | --- | --- |
| R1 | `python evaluate.py --config static -n 40 --seed 42 --threshold 0.80` | the width run of 1c — **not paired** (other graph, other n) | the **baseline**: the rules on today's cases | ½ min |
| R2 | `python evaluate.py -n 40 --seed 42 --threshold 0.80` | R1, **paired** | the **delta** static → LLM (model A, the one in `MODEL_NAME`) | 1–2 min |
| R3 | the same command as R2 | R2, **paired** | **nondeterminism**: flips without any change | 1–2 min |
| R4 | `python evaluate.py --model <model B> -n 40 --seed 42 --threshold 0.80` | R3 (model A), **paired** | the model swap: does B differ from A by more than R3 flipped? | 1–2 min |

The minutes assume about one second per model call; the evaluator runs four cases at a time. `python check_llm.py` lists the models the endpoint offers — take model B from there, or the one named on-site.

**What to read in each output:**

* **the table:** accuracy and interval per method, p95 latency, *refusal violations*, and *LLM answered k/n* — how many cases the model answered rather than the rule. An LLM run with `LLM answered 3/40` measures the rule.
* **the paired block:** b, c and McNemar p per method. In R2 it is the delta of the lecture's question. In R3 it is pure noise — remember how many cases flipped. **A model swap (R4) that flips no more cases than R3 shows nothing.**
* **the quality gate:** three clauses, each with what was measured, and PASS or FAIL.

### The other flags — reference, do not run them now

```bash
python evaluate.py --method address_recognition -n 40    # one method only
python evaluate.py --data benchmark/data/catalog.ttl     # a specific knowledge graph file
python evaluate.py --workers 1                           # one case at a time (a strict endpoint limit)
python evaluate.py --verbose                             # every case, not only the failures
```

**Check for the whole task:** `results/history.jsonl` has R1–R4 after the width run, R2–R4 each carry a paired comparison (`paired_with_previous`), and for R2 and R4 you can say whether the delta is larger than the flips of R3.

> **Budget.** One case is one model call, and `pizza_and_address` makes two: an LLM run of the plan is 160 calls. If the endpoint is slow or rationed, keep the plan and drop R3 last — never shrink `n` below 16: then not even a perfect run can pass 0.80.

## Task 5 — the report and the decision [10 min]

*Slides: 3.15 (the quality gate and the decision rule), 3.36 (the quality report), 3.38 (static vs LLM over the same cases), 3.10 (error categories).*

`quality-report.md` was written by the last run. Open it. It has what makes a number honest — commit, model, `n`, seed, the graph's hash, date, wall clock — a row per method, the quality gate with every clause, the paired comparison with the run before, and the table of every run so far with the gate and the pairing of each.

Do three things:

1. **Read the quality gate out loud** in your team, and compare its threshold with the commit of Task 4.0. If it says FAIL, there are exactly two honest responses: make the component better, or decide on a larger `n` — before the next run, with a fresh seed, and report every run. Lowering the threshold after seeing the number is not one of them.
2. **Decide which configuration and which model ship** with the decision rule: *ship the cheapest configuration that passes the quality gate; a costlier one ships only with a paired win over it on the same cases (McNemar p < 0.05).* The static rule is the cheapest; between two models, the cheaper or faster one. "Neither passes" is a decision too: nothing changes in production, and the open list says why.
3. **Complete `quality-notes.md`** — a file of your own next to the report; `evaluate.py` rewrites `quality-report.md` on every run, so nothing typed into it survives:

```text
threshold: address_recognition >= 0.80, pizza_recognition >= 0.80, pizza_and_address >= 0.80 -- because ...   (Task 4.0, committed before R1)
coverage:  addresses 8 -> 18, cities 8 -> 18; capacity address_v2 2148 -> ...
interval:  address_recognition, width run n=10: [..., ...]  ->  R2 n=40: [..., ...]
noise:     R3 flipped ... case(s); R4 against R3: b=..., c=..., p=...
failing:   "<one generated sentence your bot gets wrong>" -- category: <one of the error-analysis slide 3.10, or a new one>
decision:  <configuration and model> ships / nothing ships -- because <the clause or the pairing that decided>
```

**Commit** `quality-report.md`, `quality-notes.md`, `results/` and your extended graph together.

## Troubleshooting

| what you see | what it means | what to do |
| --- | --- | --- |
| `address_recognition` accuracy near 0.00 | the Pizza API is unreachable, so every address fails validation | `python pizza_api_stub.py` in a second terminal, `PIZZA_API_BASE=http://127.0.0.1:8000` in `.env` |
| `pytest -q` slow, a test skipped with "did not answer in time" | the shared Pizza API is under load; the live comparison skips instead of failing | run `pytest -q` again later, or use the stub |
| `no LLM configuration to measure` | `evaluate.py --config llm` without the three LLM lines in `.env` | fill them (provided on-site); until then, `--config static` |
| tests skipped with `BOT_CONFIG=llm needs …` | the same, for pytest | the same |
| `at n=… not even … of … can pass` | `n` is below `3.84·t/(1−t)` | that run can show the width of the interval, not decide; use `-n 40` |
| `not paired -- different knowledge graph` (or n, seed) | the two runs did not see the same cases | expected after you changed the graph; pair R2 with R1, not with a run from before Task 3 |
| `LLM answered` far below n | the model's answers fail the checks, or the endpoint fails, and the rule answers | `python check_llm.py`; read a few cases with `--verbose` |
| `UserWarning: … cases requested, but the catalog can only produce …` | your `-n` is larger than the capacity of that benchmark | Task 3: add individuals and wordings — or lower `-n` |
| `… .ttl: not valid Turtle -- …` | a syntax error in the named file | look for `;` or `,` where the statement should end with `.`, or a missing quote |
| `pytest -q` red after editing the Turtle file | a data rule broke | read the assertion: it names the individual and the rule (duplicate wording, missing `:name`, city defined twice, a wording the service refuses) |
| `pytest -q -m gate` red | you have not finished Task 2 or Task 3 | the message says which list or count is missing |
| `GET /city -> HTTP 404` | `PIZZA_API_BASE` in `.env` points at a stub without the endpoint (the one of Exercise 2), or `pizzabot/pizza_api.py` is still the adapter of Iteration 2 | delete the line, take this folder's adapter, or start this folder's `python pizza_api_stub.py` |
| `benchmark.fetch` refuses a city you are sure exists | the service lists it under another spelling (`Athens`, not `Athina`; `Chalandri`, not `Halandri`) — the tool says which; an abbreviation (`Ag. Paraskevi`) it cannot expand | `python -m benchmark.fetch cities --search <a part of the name>` and copy the spelling it prints |
| `results/last-run.json` not found after a run | you ran the script from another directory | run it from the folder that contains `evaluate.py` |
| R3 differs from R2 although nothing changed | the LLM configuration is nondeterministic | that is the point of R3 — write the number of flips into `quality-notes.md` |

## What is in this folder

```

tests/                    the infrastructure tests, plus your two task files
results/                  written by the evaluator: last-run.json and history.jsonl (committed)
quality-report.md         generated by the evaluator (committed)
```
